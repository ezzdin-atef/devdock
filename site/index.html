01 · Projects

All your projects, organized your way.

One page for everything you work on, across drives and folders, arranged the way you think about it.

Problem

Projects are scattered across D:\dev, C:\work and old clones. A long flat list doesn't say which ones belong together, and getting to one means browsing folders first.

How DevDock fixes it

DevDock finds your projects, detects their type and lays them out as cards. Sort them into your own groups, drag them into any order, and open any one full width with a click.

  • Groups work like folders: name them, pick one of 18 colours or any custom colour, and reorder them by dragging.
  • Drag and drop projects onto a group, or between two projects to set your own order. A clear line shows where it lands.
  • Three layouts - folders, cards or compact rows - in three sizes. Choose which details show: running state, Git, packages, type, last opened, path.
  • Group the page by your groups, by folder on disk or by type, or see everything in one grid. Sort by recent, name, type or your manual order. A favourites row sits on top.
  • Add folders with the picker or by dropping them on the window, or let scan roots find them. Type detection for Next.js, Node, Rust, PHP and Docker Compose.
  • Right-click any project for its menu. Moved or deleted folders are flagged with Locate... or Remove, and Remove never touches the folder on disk.

02 · Git

Know every repo's state, and act on it safely.

Branch, sync status and pending changes wherever a project appears, and the everyday Git actions one click away.

Problem

You start work on the wrong branch, or forget uncommitted changes from two days ago. Switching branches or pulling the latest means a terminal and a few commands, project by project.

How DevDock fixes it

DevDock reads Git through the git CLI and shows the facts on every card and in a Git tab, with buttons for the safe, common actions. Pull only fast-forwards, so DevDock never merges or rebases on its own.

  • Switch branches from a searchable picker (handy when a repo has hundreds), or check out a remote branch with tracking set up.
  • New branch, Fetch, Pull and Push, with ahead / behind counts on the buttons. A first push sets the upstream for you.
  • Every action shows a plain result ("Pulled 3 commits") with git's own output one click away. If the branches have diverged, it says so and changes nothing.
  • Staged, modified and untracked counts, the last commit, remotes, worktrees and every branch with its upstream.
  • Works for projects inside a shared monorepo and for Git worktrees.

03 · Files

Check a file, fix a line, find a name - right here.

A file tree, an editor and search across every file, inside the project you already have open.

Problem

Checking one value in .env or fixing a single line means waiting for a whole editor to open. Finding where a function is used means another window and another search box.

How DevDock fixes it

Each project has a Files tab: open a file from the tree, edit it in a CodeMirror editor, save with Ctrl S. Ctrl Shift F searches every file with ripgrep's own libraries.

  • Syntax highlighting for dozens of languages, loaded only when a file needs them, with folding, bracket matching and in-file find. Colours follow the light or dark theme.
  • Autocomplete from the language and from words already in the file - no language servers running in the background.
  • Search respects .gitignore and skips binaries, with match case, whole word, regex and include / exclude patterns. A result opens the file with the match selected.
  • Saves keep CRLF or LF and the BOM, so a save never becomes a whole-file diff, and go through a temporary file so a crash can't leave half a file.
  • Edits are safe: unsaved changes survive switching tabs and projects, and opening another file or quitting asks first. If the file changes on disk, you choose what wins.
  • Dotfiles and .git show dimmed, and the eye button hides them. Nothing outside the project folder can be opened.

04 · Run & logs

Dev servers you can actually stop.

Start scripts with a click, give them ports that never clash, read their output full height, and stop the whole thing.

Problem

Closing a terminal often leaves orphaned node.exe processes behind, still holding ports. Two projects both want port 3000. And a small terminal pane is a poor place to read logs.

How DevDock fixes it

Each run lives inside a Windows Job Object, so stopping it - or quitting DevDock - ends the entire process tree. Commands can get their own saved port, and a dedicated Logs tab gives the output the whole window.

  • Lists package.json scripts and runs them with the right package manager - npm, pnpm, yarn or bun - picked from the lockfile. Add your own commands per project.
  • Ports per command: the server's default, auto (a free port picked once and saved) or fixed. DevDock passes it as PORT and adds --port for tools like Vite, Astro and Angular.
  • A full-height Logs tab with search, stdout / stderr filters and follow.
  • Clear a log, a finished run, a project's history, or everything at once from Settings.
  • The Running screen shows everything DevDock started, with logs, stop, restart and Stop everything. Quitting with active runs asks first.

05 · Local addresses

Open shop.localhost, not localhost:3000.

Every project gets a stable, readable address, with the port hidden and HTTPS when you want it.

Problem

Every project fights over localhost:3000, so they share cookies and logins, bookmarks break whenever a port changes, and nothing tells you which tab is which project.

How DevDock fixes it

Each project gets a name like shop.localhost - browsers send these to your own machine with no setup. A small built-in proxy forwards each name to whatever that project is running, so the port drops out of the address.

  • Each address is its own site, so cookies and storage no longer leak between projects.
  • Hide the port for every project or just some. The proxy listens only on this computer, and if another server already holds port 80 it shares it automatically.
  • HTTPS: DevDock signs a certificate for each address with its own local authority, limited to .localhost and .test names, so it can never vouch for a real website. Windows asks you to confirm before trusting it.
  • Prefer .test? DevDock adds it to the hosts file after a Windows permission prompt.
  • Change a project's name and ending, copy the address or open it from the project's Overview.

06 · Packages

Installed, out of date, or not yet?

Know before you run it whether a project's packages are there, and install them with one button.

Problem

You open a project after a while, run dev, and it fails because node_modules is missing or a pull changed the lockfile. Then you work out which package manager it uses.

How DevDock fixes it

DevDock checks each project's lockfile against its last install with simple file checks - nothing runs - and marks the projects that need attention. One button runs the right install command.

  • Works with npm, pnpm, yarn (including Plug'n'Play) and bun, picked from the lockfile.
  • Not installed, out of date (the lockfile changed since the last install) or installed, shown on the project card and in its Overview.
  • The install streams its log right in the panel, with Stop. It also shows under Run, Logs and the Running screen.

07 · Security

Know what's vulnerable, what leaked, and what fixes it.

One button runs the security scanners you'd use anyway, merges what they find, and tells you which upgrade fixes it.

Problem

Checking a project means remembering five tools, their flags and their output formats. Each reports the same advisory differently, none says what to upgrade, and a leaked key in a config file goes unnoticed.

How DevDock fixes it

Each project has a Security tab. Scan project runs every scanner that applies, folds duplicates into one list, groups them by package with the version that fixes them, and keeps the report so the next scan shows what changed.

  • Seven scanners: Grype, OSV-Scanner and your package manager's audit (npm, pnpm, yarn or bun) for vulnerable dependencies, cargo audit for Rust, Trivy for Dockerfile, Compose, Kubernetes and Terraform settings, Gitleaks and Trivy for secrets, and Semgrep for risky code.
  • One finding per problem: the same advisory from several scanners is matched by its GHSA, CVE and RustSec ids, keeps the highest severity, and lists every scanner that saw it.
  • Recommended upgrades per package, worst first, with dev-only packages marked. Misconfigurations and code issues show how to fix them and open at the right line in the Files tab.
  • Install from the app: a missing scanner installs with one click - from its GitHub release, checked against its published SHA-256, into DevDock's own folder with no admin rights - or with pip or cargo. Progress and a live log show every step.
  • Secrets stay secret: only the rule, file and line are kept, never the value. Git history is scanned when you ask.
  • Export report writes a self-contained HTML file with the summary, upgrades, findings and which scanners ran - ready to share or print to PDF. The project card flags critical findings and secrets.

08 · Ports

"Port 3000 is in use" - now with an answer.

See every listening port, which process and project holds it, and whether it is safe to end.

Problem

A server fails with EADDRINUSE. Finding the culprit means netstat -ano, a PID lookup in Task Manager, and a guess about whether killing it will break something else.

How DevDock fixes it

DevDock reads the system TCP table, matches each port to its process and project, and labels the owner. Before a launch it checks the ports the command needs, and if one is taken it tells you who holds it and what you can do.

  • Every listening TCP port with PID, process name, matched project and owner: DEVDOCK EXTERNAL SYSTEM.
  • Conflict check before launch: start on another port, inspect the holder, or end it.
  • Ending an external process always asks first and shows its command line, folder, start time and child processes.
  • System processes are never offered for ending. Ownership is never guessed from a port number or executable name alone.

10 · Workspaces

Bring up the whole stack with one click.

A named group of services from one or more projects, started as one unit, in order, healthy before the next one begins.

Problem

Real work rarely means one server. It's a database, then an API that needs the database, then a frontend that needs the API - started by hand, in order, waiting and checking each time. When one crashes, you find out late.

How DevDock fixes it

Describe the stack once. DevDock starts each service in order, waits until it is actually healthy, restarts it if it crashes, and shows all logs together - labelled by service.

  • Each service is a project command (optionally in one of its Git worktrees) or a Docker Compose service.
  • Start order, optional explicit dependencies, and a port used for conflict checks.
  • Health checks: TCP (something accepts a connection on the port) or HTTP GET (a specific status, or any 2xx/3xx).
  • Restart policy: restart on crash, by default up to 3 times in 5 minutes - then stop and tell you.
  • Combined logs with per-service filters.
  • After start preset: open the editor and/or an agent once everything is up.

Safety rules

A tool that can stop processes has to be trustworthy.

These are product invariants, not settings. They are enforced in the Rust core, not left to the UI.

Never ends a process it didn't start - without asking

External processes require explicit confirmation that shows the command line, folder, start time and children.

Never touches system processes

They are labelled SYSTEM and are never offered for ending.

Changes a repository only when you click

Reading Git never writes anything. Switch, pull and push run only from their buttons, pull only fast-forwards, and DevDock never merges, rebases, commits, resets or stashes.

Never deletes folders, and writes only what you save

Remove only removes the entry from DevDock. The Files tab writes a file only when you save it, never overwrites one that changed on disk without asking, and can't open anything outside the project.

Always stops the whole process tree

Runs live in Job Objects. Quitting with active runs asks first, then stops all of them - no orphans.

Never guesses port ownership

Ownership comes from the system TCP table and process details, not from a port number or an executable name.

Asks Windows before changing Windows

Writing the hosts file needs your OK in the Windows permission prompt, and trusting the certificate shows Windows' own dialog. Nothing changes without it.

Local addresses stay local

The proxy listens only on this computer, and DevDock's certificate authority can only sign .localhost and .test names - never a real website.

Installs only what it can verify

Scanners come from their own project's GitHub releases and are checked against the SHA-256 the project publishes; a mismatch is deleted. They go in DevDock's own folder, with no admin rights, and Remove deletes them.

Never keeps a secret it finds

A security scan records the rule, file and line of a possible secret - never its value - so neither the saved scan nor the exported report can leak it again.

Under the hood

Small, native and strict.

  • Rust core owns all state and all user-facing error text; the Svelte 5 UI only renders and sends commands.
  • Tauri 2 uses the system WebView2 - no bundled browser, a small install.
  • Windows specifics (Job Objects, TCP table, process details) are isolated in one platform crate - the only place unsafe is allowed.
  • clippy::unwrap_used is denied workspace-wide; integration tests create real Git repositories.
  • CI runs fmt, clippy, tests, type checks and a WCAG contrast check on every push.

FAQ

Questions you might have.

Is DevDock free?

Yes. It's open source under the MIT license, with no paid tier, account or sign-up.

Does it work on macOS or Linux?

Not yet. DevDock is built for Windows 10/11 x64. Platform-specific code is isolated behind traits in its own crate, so the core is portable, but only Windows is supported today.

Does it send any data anywhere?

No. There is no telemetry, no account and no sync; your project list stays in a local JSON file. Installed builds check GitHub Releases for updates, and Git's fetch, pull and push talk to your own remotes when you click them. A security scan you start runs scanners that look up advisories: package audits and OSV-Scanner send your dependency list to their databases, Grype and Trivy download theirs, and Semgrep downloads its rules (with its metrics off). Your code is never uploaded.

Do I need to install the security scanners myself?

No. The Security tab lists each scanner and installs a missing one with one click - from its GitHub release, checked against its SHA-256, into DevDock's own folder. Semgrep needs Python and cargo audit needs Rust; scanners already on your PATH are used as they are.

Will it change my Git repositories?

Only when you click a button. Showing status never writes anything. Switch, new branch, fetch, pull and push run when you ask, pull only fast-forwards, and DevDock never merges, rebases, commits, resets or stashes. If a pull would need a merge, it tells you and leaves the repository alone.

How does shop.localhost work without any setup?

Browsers already send every *.localhost name to your own computer. DevDock gives each project a name and runs a small proxy on this computer that forwards it to the project's running server, so you don't need the port. Nothing is reachable from other machines.

Can it kill something important by accident?

No. It only stops processes it started without asking. Ending anything else requires a confirmation that shows the full details, and system processes are never offered at all.

Does it replace VS Code, my terminal or my Git client?

No - it opens them. DevDock is a launcher and dashboard that removes the steps between you and the tools you already use.

Which project types are detected?

Next.js, Node, Rust, PHP and Docker Compose, from their marker files. Any other folder can still be added and given custom commands.

An agent shows "not installed". What do I do?

Install it (for example npm install -g @anthropic-ai/claude-code) so it's on PATH, then click Re-check in the Agents tab.

I can't end a process on the Ports screen.

It may need elevation. Run DevDock as administrator. System processes are intentionally never offered.
