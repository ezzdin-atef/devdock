DevDock - Projects / Overview

The problem

A normal dev day leaks time in small, repeated pieces.

None of these is a disaster on its own. Together, across several local projects, they add up to dozens of interruptions a day. DevDock turns each one into one or two actions.

Before

Hunt for the folder, then open Explorer, the editor and a terminal one by one, cd-ing each time.

With DevDock
Ctrl K, type part of the name, press Enter, click your editor.

Before

Forget which branch a project is on, or whether it has uncommitted work, until you run git status.

With DevDock
Branch, ahead/behind and changed counts sit on every project row and overview.

Before

Five terminals running npm run dev, and no idea which one is which, or which ones are still alive.

With DevDock
One Running screen lists every process it owns, with logs, ports and stop buttons.

Before

Error: listen EADDRINUSE :::3000 - and no quick way to see who holds the port or if it's safe to stop.

With DevDock
A conflict check before launch names the holder and offers a safe next step.

Before

Open a terminal, cd into the right folder, then start Claude Code or Codex - every single time.

With DevDock
One click (or Ctrl Alt 1) opens the agent already in the project.

Before

Start the database, then the API, then the frontend, by hand, in the right order, waiting for each one.

With DevDock
A workspace starts them in order, waits on health checks, and restarts crashes.

The approach

It organizes your tools instead of replacing them.

DevDock is not another IDE, Git client, terminal or AI chat window. Every action ends in a real tool you already use - Explorer, your editor, Windows Terminal, an agent CLI - opened in the right folder. You keep your workflow; DevDock removes the steps between you and it.

01 · Projects

All your projects, found and typed for you.

A single list of everything you work on, across drives and folders, with the right actions one click away.

Problem

Projects are scattered across D:\dev, C:\work and old clones. Getting to one means browsing folders and then opening each tool separately.

How DevDock fixes it

Add folders directly or point DevDock at scan roots; it finds the projects below them, detects their type, and gives each one buttons for Explorer, your editor, a terminal and an agent.

  • Add with the folder picker, by dropping a folder onto the window, or with scan roots searched to a depth you choose. Scans skip node_modules, target, .next, vendor and .git.
  • Type detection from marker files: Next.js, Node, Rust, PHP and Docker Compose.
  • Search by name or path, sort by recent, name or type, filter by type, and pin favourites.
  • Paths are normalized, so the same folder can never be added twice. Projects new from a scan are marked until you look at them.
  • Moved or deleted folders are flagged with Locate... or Remove - and Remove never touches the folder on disk.
  • Opens in VS Code, Cursor, VS Code Insiders, Windsurf or Zed.

02 · Git (read-only)

Know the state of every repo before you touch it.

Branch, sync status and pending changes, shown wherever the project appears - without DevDock ever writing to your repository.

Problem

You start work on the wrong branch, or forget you left uncommitted changes in a project two days ago. Finding out means opening a terminal and running git status in each one.

How DevDock fixes it

DevDock reads Git through the git CLI and surfaces the facts you need on the project row and in a dedicated Git tab. It is strictly read-only, so it can never get in the way of your own Git workflow.

  • Repository root, current branch, upstream, and ahead / behind counts.
  • Staged, modified and untracked counts, plus the last commit's hash, message, author and time.
  • Remotes and worktrees listed in one place.
  • Works for projects inside a shared monorepo and for Git worktrees.
  • Results are cached, so the list stays fast with many repositories.

03 · Run

Dev servers you can actually stop.

Start scripts with a click, watch live output, and stop the whole thing - every child process included.

Problem

Closing a terminal often leaves orphaned node.exe processes behind, still holding ports and memory. And with several terminals open, you lose track of what runs where.

How DevDock fixes it

Each run lives inside a Windows Job Object. Stopping it - or quitting DevDock - ends the entire process tree, not just the shell. A single Running screen shows everything DevDock started, across all projects.

  • Lists package.json scripts and runs them with the right package manager - npm, pnpm, yarn or bun - picked from the lockfile.
  • Add your own custom commands per project (e.g. cargo watch -x run, php artisan serve).
  • Live console with stdout and stderr together, a filter, follow-output, and highlighted stderr.
  • Clear states: running, stopped, exited (with code), failed (with code). Detected ports are shown as soon as they listen.
  • The Running screen has logs, stop, restart and Stop everything. Quitting with active runs asks first.

04 · Ports

"Port 3000 is in use" - now with an answer.

See every listening port, which process and project holds it, and whether it is safe to end.

Problem

A server fails with EADDRINUSE. Finding the culprit means netstat -ano, a PID lookup in Task Manager, and a guess about whether killing it will break something else.

How DevDock fixes it

DevDock reads the system TCP table, matches each port to its process and project, and labels the owner. Before a launch it checks the ports the command needs, and if one is taken it tells you who holds it and what you can do.

  • Every listening TCP port with PID, process name, matched project and owner: DEVDOCK EXTERNAL SYSTEM.
  • Conflict check before launch: start on another port, inspect the holder, or end it.
  • Ending an external process always asks first and shows its command line, folder, start time and child processes.
  • System processes are never offered for ending. Ownership is never guessed from a port number or executable name alone.

05 · Agents

Your coding agent, already in the right folder.

Launch Claude Code, Codex or OpenCode in the project - or a subfolder - in the terminal you prefer.

Problem

Every agent session starts with the same ritual: open a terminal, cd to the project (or the right package in a monorepo), then type the agent's command. Get the folder wrong and the agent works in the wrong context.

How DevDock fixes it

DevDock detects which agent CLIs are installed and opens them in a real terminal at exactly the right path. Bind your favourite launches to keyboard shortcuts and it's one keystroke.

  • Detects Claude Code (claude), Codex (codex) and OpenCode (opencode) on PATH and shows where each was found.
  • Missing agents show an install hint and a Re-check button - no restart needed.
  • Launch in Windows Terminal, PowerShell, Git Bash or Command Prompt.
  • Choose the project root or any subfolder.
  • Bind up to nine launches to Ctrl Alt 1-9.

06 · Workspaces

Bring up the whole stack with one click.

A named group of services from one or more projects, started as one unit, in order, healthy before the next one begins.

Problem

Real work rarely means one server. It's a database, then an API that needs the database, then a frontend that needs the API - started by hand, in order, waiting and checking each time. When one crashes, you find out late.

How DevDock fixes it

Describe the stack once. DevDock starts each service in order, waits until it is actually healthy, restarts it if it crashes, and shows all logs together - labelled by service.

  • Each service is a project command (optionally in one of its Git worktrees) or a Docker Compose service.
  • Start order, optional explicit dependencies, and a port used for conflict checks.
  • Health checks: TCP (something accepts a connection on the port) or HTTP GET (a specific status, or any 2xx/3xx).
  • Restart policy: restart on crash, by default up to 3 times in 5 minutes - then stop and tell you.
  • Combined logs with per-service filters.
  • After start preset: open the editor and/or an agent once everything is up.

07 · Command palette

Everything is Ctrl K away.

One fuzzy search across projects, commands, agents, workspaces and ports.

Problem

Even a good UI costs clicks: pick the screen, find the project, open the tab, press the button. When you know what you want, navigation is overhead.

How DevDock fixes it

Type what you mean. The palette understands project names, commands in context and port numbers, and runs the action directly.

  • Jump to a project: type part of its name and press Enter.
  • Run a command in context: run dev in api.
  • Ask about a port: who's on 8069?
  • Start a workspace or an agent launch without leaving the keyboard.
  • Opens and closes from anywhere in the app.

08 · Settings & updates

Your tools, your theme, your data.

DevDock adapts to the tools you already have and keeps itself up to date safely.

Problem

Tools that assume one editor or one terminal force you to change your setup. Tools that update silently - or never - are hard to trust.

How DevDock fixes it

Settings shows exactly which tools were detected and where, lets you pick defaults, and handles updates with signed, verified packages from GitHub Releases.

  • Pick your editor, terminal and default agent; see every detected tool and its path.
  • Manage scan roots and scan depth.
  • Dark and light themes - follow Windows or choose manually, with a toggle in the title bar. Both meet WCAG AA contrast.
  • Data location, export and import of your whole setup.
  • In-app updates: an Update x.y.z pill appears in the title bar when a new version is out. Updates are signed and verified.

Quick start

From install to a running stack in six steps.

Add projects

Projects → add a folder, or Settings → add a scan root like D:\dev and let DevDock find the rest.

Open one

Ctrl K, type part of its name, Enter. Click VS Code (or your editor).

Run it

Run tab → start dev. Watch the console; the port appears once it's listening.

Fix a port clash

If the port is taken, the banner shows who holds it. Pick another port or end the process after reviewing its details.

Ask an agent

Agents tab → Claude Code. A terminal opens in the project folder, ready to go.

Bring up a stack

Spaces → create a workspace, add services (db, api, web) with health checks → Start all.

Safety rules

A tool that can stop processes has to be trustworthy.

These are product invariants, not settings. They are enforced in the Rust core, not left to the UI.

Never ends a process it didn't start - without asking

External processes require explicit confirmation that shows the command line, folder, start time and children.

Never touches system processes

They are labelled SYSTEM and are never offered for ending.

Never writes to a Git repository

Git is read through the CLI for facts only. No commits, checkouts, fetches or stashes.

Never deletes project folders

Remove only removes the entry from DevDock. Your files stay exactly where they are.

Always stops the whole process tree

Runs live in Job Objects. Quitting with active runs asks first, then stops all of them - no orphans.

Never guesses port ownership

Ownership comes from the system TCP table and process details, not from a port number or an executable name.

Your data

Local-first. One JSON file. Nothing leaves your machine.

No accounts, no cloud, no sync, no telemetry. Everything DevDock knows about your setup lives in a single file you can read, back up, move or delete.

Under the hood

Small, native and strict.

  • Rust core owns all state and all user-facing error text; the Svelte 5 UI only renders and sends commands.
  • Tauri 2 uses the system WebView2 - no bundled browser, a small install.
  • Windows specifics (Job Objects, TCP table, process details) are isolated in one platform crate - the only place unsafe is allowed.
  • clippy::unwrap_used is denied workspace-wide; integration tests create real Git repositories.
  • CI runs fmt, clippy, tests, type checks and a WCAG contrast check on every push.

Install

Download, run, done.

  1. Download DevDock_x.y.z_x64-setup.exe from the latest release.
  2. Run it. It installs into C:\Program Files\DevDock (asks for admin once), adds a Start menu entry and registers devdock for Win R.
  3. WebView2 is installed if missing (it's built into Windows 11).
  4. From then on, DevDock updates itself.

FAQ

Questions you might have.

Is DevDock free?

Yes. It's open source under the MIT license, with no paid tier, account or sign-up.

Does it work on macOS or Linux?

Not yet. DevDock is built for Windows 10/11 x64. Platform-specific code is isolated behind traits in its own crate, so the core is portable, but only Windows is supported today.

Does it send any data anywhere?

No. There is no telemetry, no account and no sync; your project list stays in a local JSON file. Installed builds check GitHub Releases for updates.

Will it change my Git repositories?

Never. Git access is read-only by design: DevDock runs read commands through the git CLI to show branch, changes, commits, remotes and worktrees.

Can it kill something important by accident?

No. It only stops processes it started without asking. Ending anything else requires a confirmation that shows the full details, and system processes are never offered at all.

Does it replace VS Code, my terminal or my Git client?

No - it opens them. DevDock is a launcher and dashboard that removes the steps between you and the tools you already use.

Which project types are detected?

Next.js, Node, Rust, PHP and Docker Compose, from their marker files. Any other folder can still be added and given custom commands.

An agent shows "not installed". What do I do?

Install it (for example npm install -g @anthropic-ai/claude-code) so it's on PATH, then click Re-check in the Agents tab.

I can't end a process on the Ports screen.

It may need elevation. Run DevDock as administrator. System processes are intentionally never offered.
